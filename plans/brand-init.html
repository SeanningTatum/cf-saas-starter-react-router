/brand-init: choose a brand from three, then redesign the components

2026-10-23 · feature: brand-init · tier: full · in-review · round 0

TL;DR

A new command, /brand-init, interviews you with impeccable init, has taste deal three directions, and builds each one as a live comp with Emil-grade motion. You pick one in this review UI. It then redesigns the 55 shadcn primitives and the shared components in that direction, all in one PR, so every page inherits the brand without being touched. It exists because the repo's design work has gone generic every time a model chose the look alone.

Product brief

Problem and evidence

A fork of this template starts with the starter's look: neutral oklch tokens in app/app.css (every --primary, --muted and --border has chroma 0), Inter loaded from app/root.tsx:31, and no PRODUCT.md or DESIGN.md, so impeccable runs with no product context. When the repo has let a model pick the look, it has gone generic. The 2026-07-30 postmortem (c3b7202:.brain/runs/2026-07-30-design-slop-postmortem.md) records a surface that "passed every gate the repo had" and was still judged "still generic slop", failing six anti-slop checks, with "Cover the wordmark and it could be any ops SaaS" among them.

User and job

You, on the first day of a fork made with /new-app: you need the app to look like this product before anyone builds a feature on it. The second user is every later UI agent (ui-builder, impeccable, taste), whose job is to build new screens in the brand without being told it again. They read PRODUCT.md and DESIGN.md.

Success metric

No baseline number exists, so this uses a named check (tier 3). After one run on a fresh fork:

  • You were asked for input at most 3 times after the interview: the pick, the home question, and P0/P1 escalations if any. Today the count has no bound, since every surface is designed by hand.
  • The kitchen-sink page (admin/kitchen-sink.tsx, every primitive) has 0 impeccable P0/P1 findings at desktop and mobile, in light and dark.
  • grep -c "oklch([0-9.]* 0 0)" app/app.css falls from today's count to only the true neutrals the direction keeps on purpose, and brain verify is green.

Non-goals

  • A drawn logo mark. Marks drawn by models read as clip art. The wordmark is typeset; a real mark is a designer's job (grill Q3).
  • Rewriting pages. Pages inherit from the primitives. The one exception is home.tsx, and only if you say yes when asked (grill Q8).
  • Stacked PRs. This is a once-per-repo redesign, so one big PR is fine (grill Q10). Stacking belongs to /ship-stack.
  • Refero. It is removed from this project and from the global skills (grill Q7).

Plan of record

Phases 1 to 3 build the harness. Phases 4 to 6 are what one run of /brand-init does, and the dry run in phase 7 proves them.

  1. Phase 1: the command. .claude/commands/brand-init.md runs the pre-flight (clean tree, green baseline, refuses when DESIGN.md exists without --redo, one feature in progress), the impeccable init interview, the taste draw, both workflow launches, the pick review, and the close (brain doc, commit, PR). Acceptance: the command refuses on a dirty tree and on an existing DESIGN.md, saying why. Verify: run it in both states and read the refusal.
  2. Phase 2: the propose stage. .claude/workflows/brand-init.js with stage: "propose" takes three direction sheets and PRODUCT.md and returns three comps, each with tokens as JSON (shadcn roles for light and dark, fonts, radius, motion), screenshots at desktop and mobile in light and dark, and its critique scores. Acceptance: three comps that differ in palette, type and composition; each passes WCAG AA for body text in both themes; each critique is attached, with scores under 7.5 left as they are. Verify: open the three comps; check contrast with the inspector.
  3. Phase 3: the apply stage. The same script with stage: "apply" takes the chosen tokens as the contract. The contract lane goes first, then six lanes on disjoint paths (T6, shared components, and home when you said yes), then the check wave, then polish and document. It never commits and never writes to the brain. Acceptance: no lane edits outside its fence; every call site still compiles with no prop changes. Verify: bun run typecheck; a diff of each lane's files against its fence.
  4. Phase 4: the pick. The command writes plans/brand-pick.html with the three comps inlined, and opens it in brain review. Acceptance: you pick with one radio button and answer "rebuild home?" with another; the answers come back in the poll. Verify: brain plans view brand-pick shows both decision prompts.
  5. Phase 5: the gates. On the apply stage's tree: impeccable critique at desktop and mobile, in light and dark, on kitchen-sink, the dashboard and admin users; review-animations on the motion; brain verify; feature-verifier walks sign-up, the dashboard and admin. Acceptance: 0 impeccable P0/P1; review-animations passes; every gate green. Verify: the critique text pasted into the verification body, as AGENTS.md requires.
  6. Phase 6: the record. DESIGN.md (impeccable document), PRODUCT.md, brain docs set codebase design-system naming the winner, the two that lost and why, and ui-builder.md told to read DESIGN.md first. One commit, one PR in the pr-format layout. Acceptance: brain docs view codebase/design-system returns the decision; a new UI agent reads DESIGN.md before its first edit.
  7. Phase 7: the dry run. Run /brand-init on a throwaway branch try/brand-init with a sample brief, carry it through to an unmerged PR, and screenshot the result. Then drop the branch: the template keeps its monochrome, per the c3b7202 precedent. Acceptance: the success metrics above hold on the dry run. Verify: a brain verifications add brand-init PASS with the screenshots attached.
